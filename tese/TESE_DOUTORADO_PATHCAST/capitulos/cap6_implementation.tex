\chapter{Implementation}
\label{ch:implementation}

This chapter documents the software instantiation of PATHCAST
(Definition~\ref{def:pipeline}). At the time of writing, Stage~1 (event log
construction) and a preliminary Stage~2 E1 module (process discovery and
conformance) are implemented on the evaluation corpus described in
Chapter~\ref{ch:methodology}; Stages~3--4 and the ML component remain
specified but not yet integrated into the end-to-end executable pipeline
(Section~\ref{sec:impl-roadmap}).

Section~\ref{sec:impl-architecture} presents the repository layout and
technology stack. Section~\ref{sec:impl-stage1} details the Stage~1 modules
and reports harvest-scale statistics from the June~2026 snapshot.
Section~\ref{sec:impl-artifacts} lists the interim data products.
Section~\ref{sec:impl-e1-pilot} reports a single-repository E1 feasibility
pilot. Section~\ref{sec:impl-confidential} discusses the handling of
confidential organisational data used for internal validation only.

\section{Stage 1: Event Log Construction}
\label{sec:impl-stage1}

Stage~1 implements the signature $\mathcal{S}_1 : \mathcal{R} \to \mathcal{L}$
(Equation~\ref{eq:stage1-sig}). The harvest proceeds in three steps:
\begin{enumerate}
    \item \textbf{Collection.} \texttt{collector.py} retrieves issues, timeline
    events, pull requests, and (optionally) GitHub Actions runs via the GitHub
    REST API, with pagination, rate-limit handling, and retry logic.
    \item \textbf{Normalisation.} Issue and PR histories are mapped to the
    PATHCAST activity alphabet (e.g.\ \texttt{ISSUE\_OPENED},
    \texttt{PR\_MERGED}; see \texttt{xes\_builder.py}).
    \item \textbf{Serialisation.} Events are written as a columnar Parquet file
    and, on demand, as an XES~IEEE~1849-2016 log via PM4Py.
\end{enumerate}

For Jira-backed repositories (Apache and Spring projects), \texttt{jira\_collector.py}
reads transition histories from the Montgomery et al.\ public Jira dataset and
produces a separate interim log (\texttt{jira\_event\_log.parquet}, 37~MB;
tagged variant \texttt{jira\_event\_log\_tagged.parquet}, 27~MB).

\section{Preliminary E1 Feasibility Pilot}
\label{sec:impl-e1-pilot}

The \texttt{stage2\_mining} module and pilot script
(\texttt{scripts/run\_e1\_pilot\_pm4py.py}) exercise the E1 protocol of
Section~\ref{sec:e1-design} on a single public repository using PM4Py.
The pilot filters the 800 most recent cases from \texttt{fastapi/fastapi},
discovers a Petri net with the Inductive Miner at
$\theta_{\text{noise}} = 0.2$, and computes alignment-based fitness and
precision plus token-based-replay generalization.

For \texttt{fastapi/fastapi}, all four preview acceptance checks of
Equation~\eqref{eq:acceptance} are satisfied (fitness $= 0.911$,
precision $= 0.817$, coverage $= 1.00$, cases $= 800$), demonstrating
feasibility on a high-activity GitHub Issues workflow before the stratified
batch below.

Table~\ref{tab:e1-representative} reports the preliminary E1 batch executed with

All ten repositories pass every preview acceptance check in
Equation~\eqref{eq:acceptance}. Alignment-based fitness ranges from
0.886 (\texttt{cli/cli}) to 1.000 (\texttt{django/django},
\texttt{facebook/react}); the two Jira-backed entries
(\texttt{apache/kafka}, \texttt{spring-projects/spring-framework}) lie at

batch caps at 800 cases per repository, several GitHub projects still yield
fewer than 100 traces under Stage~1 filtering, and external validity requires
the complete E1 aggregate defined in Section~\ref{sec:e1-design}.

\section{Confidential Organisational Data}
\label{sec:impl-confidential}

During internal development, event logs extracted from a confidential
organisational environment (Jira and Bitbucket projects) were used
\emph{off-line} to stress-test Stage~1 activity mapping and PM4Py
integration. These data are subject to organisational terms of use and are
not part of the public evaluation corpus (Chapter~\ref{ch:methodology}).

\paragraph{Anonymisation assessment.}
A field-level review of the raw exports identifies the following
re-identification risks if published without transformation:
\begin{itemize}
    \item \textbf{Direct identifiers:} employee names in the \texttt{Author}
    column; Atlassian URLs containing the organisation domain; issue titles
    describing internal deliverables; and project keys.
    \item \textbf{Quasi-identifiers:} exact timestamps at second resolution;
    rare activity sequences combined with status labels customised to the
    organisation's workflow.
    \item \textbf{Lower risk (aggregates):} DFG edge counts, bottleneck tables
    by status name, fitness/precision on pseudonymised logs, and variant
    \emph{structure} without titles or authors.
\end{itemize}

\paragraph{Thesis reporting policy.}
Unless explicit written authorisation is obtained from the data controller,
\emph{no record-level export from the confidential corpus appears in this thesis
or in the public replication package}. Permitted uses without authorisation are:
\begin{enumerate}
    \item methodological prose describing pseudonymisation (URL removal, author
    hashing, title redaction, date shifting);
    \item fully synthetic substitute logs (generated internally by
    \texttt{assess\_flow\_pmo\_anonymization.py}); and
    \item \emph{aggregate-only} statistics that cannot reasonably identify the
    organisation, provided custom workflow status names and deliverable titles
    are omitted (Table~\ref{tab:flow-pmo-anonymous}).
\end{enumerate}

\paragraph{Anonymised aggregate statistics.}
Four confidential Bitbucket/Jira projects from a single industrial partner are
denoted P\textsubscript{1}--P\textsubscript{4}. Table~\ref{tab:flow-pmo-anonymous}
reports volume counts and E1 preview conformance on the PATHCAST Bitbucket
activity alphabet only (commit and pull-request lifecycle events; author and
title fields stripped before mining). A full Jira transition log is available
for P\textsubscript{1} (987 cases, 6{,}916 events, 36 activities); the
remaining projects contribute Bitbucket snapshots and downstream issue tables
without exported transition histories. Across the three projects with pull-request
traces, the E1 preview acceptance criteria of Equation~\eqref{eq:acceptance}
are satisfied (fitness $0.967$--$0.991$; precision $0.740$--$1.000$).

\input{results/auxiliary/aux_flow_pmo_anonymous}

Even when status labels appear generic, the combination of labels, volumes, and
timing could fingerprint the organisation; Table~\ref{tab:flow-pmo-anonymous}
therefore excludes workflow status names, DFG edges, bottleneck stage labels, and
variant strings. A formal anonymisation protocol and legal review remain
prerequisites for any richer disclosure.

\section{Implementation Roadmap}
\label{sec:impl-roadmap}

The remaining milestones follow the PathCast development roadmap (v0.2--v0.6):
Stage~3 Markov estimation with Laplace smoothing for sparse transitions;
Stage~4 Monte Carlo simulation with percentile extraction; end-to-end CLI
orchestration; full E1 over all qualifying repositories and complete E2
forecasting evaluation. Upon completion, this chapter will be expanded with
end-to-end runtime metrics, replication-package DOI, and PostgreSQL persistence
(Section~\ref{sec:data-collection}). Stage~2 E1 mining
(\texttt{stage2\_mining}) and the preliminary batch reported in
Section~\ref{sec:impl-e1-batch} are already implemented at v0.1.0.
